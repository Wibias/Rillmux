# Twitch runtime debug observability design

## Goal

Add opt-in, category-filtered runtime diagnostics for the Twitch features that are currently hard to debug from user-visible symptoms alone, especially first-start races involving Chatterino, player/HUD geometry, Channel Points credit, +50 claims, rewards, polls/predictions, and raids.

The existing `gui.debugMode` remains the master switch. New diagnostics must not change normal runtime behaviour when debug mode is off.

## Problems this must make observable

1. First stream start can show a white/black Chatterino window before the correct window appears.
2. Stream stop can report `PostMessage failed ... 0x80070578 - invalid window handle`.
3. Channel Points HUD can be positioned incorrectly on the first stream start and correctly on a later start.
4. Rewards can load while passive watch credit still does not increase the balance.
5. Timed +50 bonus auto-claim still does not succeed.
6. Polls/predictions and raid-follow paths need enough trace data to distinguish subscription, overlay, mutation and window-placement failures.

## Debug categories

Add six independently selectable categories under the existing Debug Mode setting:

- `windows`: stream lifecycle, mpv, Chatterino, HWND validity, layout and overlay geometry.
- `points-credit`: viewer-presence target selection, Hermes auth/subscriptions, minute-watched telemetry and balance deltas.
- `points-claim`: available claim discovery, +50 claim attempts and outcomes.
- `rewards`: ChannelPointsContext selection, reward catalogue parsing and reward redemption.
- `polls`: poll/prediction subscriptions, fallback reads, overlay lifecycle and point-spend mutations.
- `raids`: EventSub state, raid event receipt, dedupe, countdown, old/new session transitions and overlay placement.

When Debug Mode is first enabled, all categories default to enabled. Users may disable individual categories. Turning Debug Mode off disables all category output without losing the category preferences.

## Event format

All category diagnostics use one chronological stream and the existing `rillmux.log` destination.

Each event has:

- wall-clock timestamp generated by the diagnostics writer;
- severity (`DBG`, `WARN`, `ERR`);
- category;
- event name;
- optional correlation fields such as channel login, session id, generation and HWND;
- compact key/value fields.

Example:

```text
[11:42:08.173][DBG][windows][channel=foo][session=abc] chatterino.open.request generation=4
[11:42:08.411][DBG][windows][channel=foo][session=abc] chatterino.hwnd hwnd=0x001A04CE valid=true rect=10,20,420,900
[11:43:00.012][DBG][points-credit][channel=foo] minute_watched.sent status=204
[11:43:02.184][DBG][points-credit][channel=foo] balance.delta before=12450 after=12450 delta=0
```

## Diagnostics transport

Do not synchronously write every new event on the hot path.

Extend the Rust diagnostics module with a bounded asynchronous queue and a single writer task/thread:

- producers perform category checks before enqueue;
- queue is bounded;
- enqueue is non-blocking;
- on overflow, events are dropped and a drop counter is emitted later;
- the writer owns timestamp formatting and writes to console plus `rillmux.log`;
- existing always-on error logging remains available for important failures regardless of category filters;
- current 10 MiB rotation behaviour stays intact.

The design must avoid making Chatterino/window races disappear merely because debug logging changes timing.

## Settings model and UI

Add persisted debug category preferences under `gui` rather than under `streaming`, because these controls describe diagnostics, not feature behaviour.

Suggested shape:

```ts
debugCategories: {
  windows: boolean;
  pointsCredit: boolean;
  pointsClaim: boolean;
  rewards: boolean;
  polls: boolean;
  raids: boolean;
}
```

Bump the settings schema and migrate old settings so all categories default to `true` when absent.

Under `Settings > General`, keep the existing Debug Mode row. When Debug Mode is on, show a compact `Debug output` section with six checkboxes and the existing `Open logs` action.

The main window remains the only owner of the debug console. Overlay webviews must not independently toggle diagnostics or persist settings.

## Instrumentation points

### Stream / Windows / Chatterino

Instrument both frontend orchestration and native window code so one timeline can reconstruct a first-start race.

Log:

- `watchStream` entry and resolved launch options excluding secrets;
- `stream_start` request/return and session id;
- stream status phase/ready transitions;
- Chatterino sync key, generation, open/close request and completion;
- discovered Chatterino HWND, hexadecimal handle, `IsWindow` result, ownership and rect;
- each layout request with planned channels, chat reservation and target rects;
- native layout application with actual HWND rects;
- HUD placement request and final native rect;
- stop/destroy order;
- every failed native window message with operation, handle, `IsWindow` result and Win32 error code.

Never retry an invalid handle merely because debug mode is enabled.

### Channel Points watch credit

Instrument the complete credit chain rather than Hermes only.

Log:

- frontend presence sync key and selected targets;
- metadata lookup success/failure for each watched session;
- web-auth/account match result without tokens;
- Hermes connect, authenticate, viewer-topic and playback-topic subscriptions;
- subscription acknowledgements;
- ready/not-ready transitions, reconnect reason and generation;
- minute-watched worker start/stop and each telemetry attempt;
- telemetry HTTP result and compact Twitch error information;
- Channel Points balance snapshots and deltas after refreshes.

This must let a log prove distinctions such as "Hermes ready but minute-watched was never sent" or "minute-watched accepted but balance stayed unchanged".

### +50 bonus claims

Log:

- whether `availableClaim` exists;
- a redacted claim id, at most a short prefix/suffix;
- reason a claim is skipped;
- selected claim auth path;
- claim attempt start;
- HTTP status and GraphQL error code/message summary;
- claim success/failure;
- balance before and after the following refresh when available.

### Rewards

Log:

- each ChannelPointsContext persisted-query candidate by short hash prefix;
- success/failure per candidate;
- whether required balance/claim state was present;
- which reward collection path matched;
- parsed reward count;
- reward redemption request with reward id redacted, cost and whether input text was supplied;
- HTTP/GQL result.

Do not log reward input text.

### Polls and predictions

Log:

- Hermes topic subscription requests and acknowledgements;
- fallback GQL activation and reason;
- poll/prediction discovered, updated and cleared;
- overlay open/close and placement rect;
- user action with choice/outcome id redacted and points amount;
- mutation HTTP/GQL result;
- resulting balance snapshot when available.

### Raids / EventSub

Log:

- EventSub enable/sync inputs;
- connect/reconnect/disconnect state;
- outgoing raid subscription creation;
- raid event receipt with from/to login and viewer count;
- dedupe decision;
- raid overlay placement and countdown lifecycle;
- follow decision;
- old session stop and replacement stream start with session ids;
- layout/HUD reconciliation after the replacement becomes ready.

## Privacy and redaction

Debug output must never include:

- OAuth tokens;
- cookies;
- device ids;
- complete authorization headers;
- complete GraphQL request/response bodies;
- reward user-input text;
- full claim ids or other high-entropy authentication-adjacent identifiers.

Persisted-query hashes may be logged only as a short prefix sufficient to identify the candidate in source.

## Error handling

Diagnostics must be best-effort. Logging failure must never fail a stream, claim, reward action, poll vote or raid transition.

The diagnostics queue must survive individual file-write errors. Existing crash/minidump behaviour remains unchanged.

## Tests

Add tests before implementation changes where practical:

1. settings migration defaults every debug category to enabled;
2. category filter blocks disabled categories and allows enabled ones;
3. redaction helpers do not expose full tokens/claim ids/hash values;
4. bounded queue cannot block producers and reports dropped events;
5. stream/Chatterino orchestration emits correlation fields at the expected lifecycle points;
6. Channel Points credit instrumentation covers target selection, Hermes readiness and minute-watched result;
7. claim instrumentation records skip, attempt and result paths;
8. reward instrumentation records query candidate and parser result without payload leakage;
9. poll/prediction and raid instrumentation covers subscription/overlay/action lifecycle;
10. `npm test`, frontend build, Rust fmt/clippy/check/test and existing security/audit gates remain green.

## Scope boundaries

This change adds observability. It does not claim to fix the remaining passive credit, auto-claim, first-start Chatterino or first-placement bugs unless instrumentation exposes an obvious low-risk defect during implementation. Any behavioural fix discovered from the new evidence should be a separate focused follow-up unless it is necessary to make the diagnostics accurate.

No new remote telemetry is added. All new debug data stays local in the existing console/log files.
